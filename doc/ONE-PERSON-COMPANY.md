## 1. 为什么一人公司是可能的

### 1.1 行业背景

Sam Altman（OpenAI CEO）在 2024 年初预言："我们离第一家由一个人运营的十亿美元公司不远了。"

这不是科幻。Indie Hackers 社区中，已有创始人：

- 用 AI 将原来需要 3 人团队的代理公司维持在 **$340K/年营收**
- **4 周内** 将 AI 编排平台做到 **$3K MRR**
- **10 个月内**独自完成产品从 0 到 **$1M ARR**

### 1.2 一人公司的本质

一人公司不是一个人什么都干，而是：

```
你（Board）= 战略家 + 决策者 + 质量把关者
AI 团队    = 执行者（工程、产品、营销、运营...）
```

你的工作从"亲自写代码、做运营"变成"定义目标、分配任务、审查结果、调整方向"。

### 1.3 Anthropic 的关键洞察

来自 Anthropic 与数十个 AI Agent 团队的实践总结：

> "最成功的实现不是用复杂框架，而是**简单、可组合的模式**。"

核心原则：
1. **保持 Agent 设计的简单性** — 单职责，不要让一个 Agent 做太多事
2. **透明化 Agent 的规划步骤** — 让你能看到 Agent 的思考过程
3. **精心设计 Agent 与工具的接口** — 清晰的任务描述比复杂的 Agent 更有效

## 2. 核心认知转变：你是 Board，不是员工

### 2.1 思维模式对比

| 旧思维（打工人） | 新思维（Board） |
|-----------------|-----------------|
| 我来写这个功能 | 我创建任务，分配给工程 Agent |
| 我来做这次调研 | 我定义调研目标和交付物，分配给研究 Agent |
| 我来处理客服 | 我设置客服 Agent 的边界和升级规则 |
| 我来写博客 | 我提供品牌调性和主题，内容 Agent 执行 |

### 2.2 你实际要做的事

作为 Board，你的日常工作是：

1. **每天早上**（10-15分钟）：查看 Dashboard，了解各 Agent 的运行状态
2. **审批队列**：处理 Agent 请求批准的事项（策略变更、超预算、关键决策）
3. **质量审查**：检查 `in_review` 状态的任务，决定接受或打回
4. **目标调整**：根据进展调整优先级，更新目标层级
5. **干预**：暂停跑偏的 Agent，手动 force-release 卡死的任务

### 2.3 Paperclip 如何支持这个模式

```
你的精力 → 放在哪？

10% 策略定义（创建公司目标 + 高层任务）
20% 审批决策（批准关键行动）
30% 质量把关（审查 Agent 产出）
40% 优化迭代（调整 Agent 配置 + 任务描述）
```

## 3. 一人公司的典型架构模板

### 3.1 最小可行 AI 公司（MVP 配置）

适合启动期，3-4 个 Agent：

```
你（Board）
└── CEO Agent（战略规划 + 任务分解）
    ├── 工程 Agent（写代码、修 Bug）
    └── 产品 Agent（需求分析、用户研究）
```

### 3.2 SaaS 产品公司（标准配置）

适合 PMF 之后，6-8 个 Agent：

```
你（Board）
└── CEO Agent
    ├── CTO Agent
    │   ├── 后端工程 Agent
    │   ├── 前端工程 Agent
    │   └── QA Agent
    └── CMO Agent
        ├── 内容营销 Agent
        └── SEO/增长 Agent
```

### 3.3 内容/媒体公司（内容驱动）

适合博客、Newsletter、课程等：

```
你（Board）
└── 主编 Agent（选题规划 + 质量审查）
    ├── 研究 Agent（收集信息、做调研）
    ├── 写作 Agent（内容创作）
    ├── 编辑 Agent（校对、优化）
    └── 分发 Agent（社媒发布、SEO）
```

### 3.4 服务/咨询公司（交付驱动）

适合 B2B 服务或代理公司：

```
你（Board）
└── 项目经理 Agent（客户管理 + 项目协调）
    ├── 分析 Agent（客户需求分析、数据分析）
    ├── 执行 Agent（实际交付物生产）
    └── 报告 Agent（客户报告、沟通材料）
```

## 4. 五个真实的一人公司场景

### 场景 A：独立开发者 SaaS

**目标**：独自开发并运营一款 B2B SaaS 工具

**挑战**：一个人写代码 + 做产品 + 做营销 + 处理客服

**Paperclip 配置：**

```
公司目标：6个月内做到 $5K MRR 的开发者工具
│
├── 工程目标：构建稳定、可扩展的 MVP
│   ├── Issue: 实现用户认证模块
│   ├── Issue: 设计数据库 Schema
│   └── Issue: 开发核心 API
│
├── 产品目标：找到 PMF
│   ├── Issue: 访谈 10 位目标用户
│   ├── Issue: 分析竞品功能矩阵
│   └── Issue: 制定功能优先级
│
└── 增长目标：获得前 100 个用户
    ├── Issue: 写 5 篇技术博客（SEO）
    ├── Issue: 在 Product Hunt 发布
    └── Issue: 建立 Twitter/X 内容矩阵
```

**Agent 配置要点：**

```json
// 工程 Agent（claude_local）
{
  "name": "Alex - 工程师",
  "adapter_type": "claude_local",
  "adapter_config": {
    "system_prompt": "你是一名专注于 SaaS 产品开发的全栈工程师。\n技术栈：TypeScript, React, Node.js, PostgreSQL。\n每完成一个功能，必须：\n1. 写单元测试\n2. 更新 API 文档\n3. 在任务评论中记录实现决策\n在任务文档 'plan' 中写出实现方案再开始编码。",

  },
  "context_mode": "thin",
  "budget_monthly_cents": 8000
}
```

```json
// 增长 Agent（process 适配器，调用内容生成脚本）
{
  "name": "Morgan - 增长",
  "adapter_type": "process",
  "adapter_config": {
    "command": "python",
    "args": ["/workspace/agents/growth_agent.py"]
  },
  "budget_monthly_cents": 3000
}
```

**工作节奏：**
- 每天检查一次 Dashboard（10分钟）
- 每周一：审查上周产出，设置本周优先级
- 每完成一个功能：手动 code review，决定是否合并

## 5. 启动你的一人公司：分步操作

### 第一步：启动 Paperclip

```sh
pnpm install
pnpm dev
# 访问 http://localhost:3100
```

### 第二步：创建公司和顶层目标

在 Board UI 中：

1. **创建公司**
   - 名称：`[你的产品名] Co.`
   - Issue 前缀：简短缩写（如 `NOVA`）
   - 月度预算：先设 $100（=10,000 分），后续调整

2. **创建顶层目标**
   ```
   标题：[具体、可量化的目标]
   示例："6个月内将 DevTools SaaS 做到 $5,000 MRR"
   级别：company
   状态：active
   ```

3. **分解为 3-5 个子目标**
   ```
   - 产品目标：构建核心功能 MVP（3个月内）
   - 用户目标：获得 100 个活跃用户（3个月内）
   - 收入目标：转化率达到 5%（6个月内）
   ```

### 第三步：按需创建 Agent（从最少开始）

**第一周：只创建 1-2 个 Agent**

从 CEO Agent 开始：

```
名称：[你取个名字] - CEO
适配器：claude_local（如果用 Claude Code）
上下文模式：thin（节省成本）
月度预算：$30（=3,000 分）
```

**Prompt 模板（CEO Agent）：**

```
你是 [公司名] 的 CEO，一家 [描述] 公司。

公司使命：[使命]
当前阶段：[早期/成长期/...]
核心产品：[描述]

你的职责：
1. 将公司目标分解为季度和月度任务
2. 识别当前最重要的 3 件事（IPO: Important/Priority/Output）
3. 创建子任务并分配给对应 Agent
4. 每次心跳结束时，在任务评论中汇报：做了什么、发现了什么、下一步是什么

决策原则：
- 优先做能产生收入或用户增长的事
- 遇到不确定的决策，在任务评论中列出选项，等待 Board 指示
- 不要超越预算限制

当前公司信息可通过 Paperclip API 获取：
- 公司ID：{company_id}
- API Endpoint：http://localhost:3100/api
- 你的 API Key：{agent_api_key}
```

### 第四步：创建你的第一个项目和任务

```
项目：MVP 开发
├── Issue: 定义 MVP 功能范围（优先级: critical）
│   描述：列出 5 个核心功能，每个功能定义完成标准
│   负责人：CEO Agent
│
└── Issue: 竞品分析（优先级: high）
    描述：分析 3 个直接竞品的功能、定价、目标用户
    负责人：CEO Agent
```

### 第五步：触发第一次心跳，观察

手动触发 CEO Agent 心跳，观察：
- Agent 是否理解任务？
- 产出质量如何？
- 评论是否清晰？

根据结果调整 Prompt，这是最重要的早期工作。

## 6. Agent 设计的核心原则

### 6.1 单职责原则

每个 Agent 只做一件事，并做好它：

```
❌ 一个 Agent 同时负责：写代码 + 写文档 + 做测试 + 做营销
✅ 四个专门 Agent，各司其职
```

### 6.2 输出标准化

在每个 Agent 的 Prompt 中明确规定输出格式：

```
每次任务完成必须：
1. 在任务评论写一份"完成总结"（50-100字）
2. 在 'deliverables' 文档记录实际交付物
3. 如果遇到阻塞，立即在评论中说明阻塞原因和需要什么资源
4. 状态改为 in_review 前，确认所有验收标准都已满足
```

### 6.3 失败处理规则

```
如果遇到以下情况，必须停止并在评论中请求帮助：
- 需要访问不存在的工具或资源
- 任务描述有歧义，可能有多种解读
- 发现风险（如修改了超出任务范围的代码）
- 3次尝试后仍无法解决某个技术问题
```

### 6.4 成本意识

在高成本 Agent 的 Prompt 中加入：

```
成本意识：
- 优先用 grep/搜索而不是重新读取整个文件
- 如果问题可以用简单方法解决，不用复杂方案
- 每次心跳的 Token 消耗不应超过预估的 20%
```

### 6.5 评估-优化循环（Evaluator-Optimizer 模式）

对于内容类 Agent，设置 Reviewer Agent：

```
生产 Agent → 输出草稿
    ↓
Reviewer Agent（评估并给出修改意见）
    ↓
生产 Agent 修改
    ↓
你（Board）最终审批
```

Reviewer Agent Prompt 示例：

```
你是一名严格的质量审核员。你的任务是评审 [具体内容类型]。

评审维度（每项1-5分）：
1. 准确性：信息是否正确，有无错误
2. 完整性：是否覆盖了所有要求的内容
3. 质量：写作/代码质量是否达标
4. 品牌一致性：是否符合公司风格

输出格式：
- 总分：X/20
- 通过门槛：16分
- 不足之处：[具体列出]
- 修改建议：[具体可操作的建议]
- 决定：通过/需要修改/退回重做
```

## 7. 任务设计与工作流最佳实践

### 7.1 好任务 vs 差任务

| 差任务 | 好任务 |
|--------|--------|
| "写一些博客文章" | "写一篇 1000 字的教程，教开发者如何用 Python 调用 OpenAI API，目标读者是 Python 初学者，SEO 关键词：openai api python tutorial" |
| "修复 Bug" | "修复用户登录后跳转到错误页面的 Bug。复现步骤：1. 登录；2. 点击'我的项目'；3. 预期跳转到 /dashboard，实际跳转到 /undefined。优先级：critical" |
| "做竞品分析" | "分析 Notion、Obsidian、Roam Research 三个产品的 AI 功能，输出一个对比表格，包含：功能列表、价格、目标用户、优劣势。交付物放在 'research' 文档中" |

### 7.2 验收标准模板

每个任务的描述应包含：

```markdown
## 目标
[一句话说清楚这个任务要达到什么]

## 背景
[为什么做这个？和哪些上下文相关？]

## 交付物
- [ ] 交付物1
- [ ] 交付物2

## 验收标准
- [ ] 标准1（可量化）
- [ ] 标准2

## 限制条件
- 不要修改 X 文件
- 不要调用 Y API
- 预算：不超过 $5 的 Token 消耗

## 参考资料
- 链接1
- 文档路径
```

### 7.3 父子任务拆分原则

超过 4 小时工作量的任务必须拆分：

```
父任务：实现用户认证系统
├── 子任务1：设计数据库 Schema（1小时）
├── 子任务2：实现注册 API（2小时）
├── 子任务3：实现登录 API + JWT（2小时）
├── 子任务4：实现密码重置流程（2小时）
└── 子任务5：写集成测试（2小时）
```

### 7.4 状态流转规则

给 Agent 明确的状态转换规则：

```
状态转换规则：
- 开始工作前：先 checkout 任务
- 遇到阻塞：立即改为 blocked，在评论说明
- 完成工作：改为 in_review，等待 Board 审批
- 不要自己把任务改为 done（由 Board 决定）
```

## 8. 成本控制策略

### 8.1 分层预算策略

```
公司月度总预算（留 20% 缓冲）
├── CEO Agent：$30/月（战略决策，用高端模型）
├── 工程 Agent：$80/月（主力，用中端模型）
├── 内容 Agent：$30/月（批量生产，用经济模型）
└── 分析 Agent：$40/月（深度分析，用高端模型）
```

### 8.2 模型分层选择

根据任务复杂度选择合适的模型：

| 任务类型 | 推荐模型 | 理由 |
|----------|----------|------|
| 战略规划、架构设计 | claude-opus-4-5 | 需要深度推理 |
| 功能开发、内容创作 | claude-sonnet-4-5 | 性价比最优 |
| 格式化、简单研究 | claude-haiku-4-5 | 高速低成本 |
| 路由和分类 | claude-haiku-4-5 | 任务简单，成本优先 |

在 Prompt 中加入成本约束：

```json
{
  "adapter_config": {
    "model": "claude-haiku-4-5",
    "system_prompt": "...你的成本预算：每次心跳不超过 $0.50 的 Token 消耗..."
  }
}
```

### 8.3 `thin` 上下文模式的使用

大多数 Agent 使用 `thin` 模式：

- **thin（推荐）**：只传递当前任务相关上下文，节省 60-80% Token
- **fat（谨慎使用）**：传递完整上下文，适合需要深度理解整体状态的 CEO Agent

### 8.4 月度预算监控节奏

```
每天：快速查看当日 Token 消耗（< 2分钟）
每周：检查各 Agent 的消耗趋势
每月：复盘 ROI（Token 消耗 vs 产出价值）
```

预算红线：
- 某 Agent 单日消耗 > 月预算 10%：立即检查
- 公司月消耗 > 80%：触发预警，审查所有运行中任务

### 8.5 Token 成本估算参考

以 Claude Sonnet 4.5 为例（截至 2026 年参考价格）：

| 任务 | 预估 Token | 预估成本 |
|------|-----------|----------|
| 写一篇 1000 字博客 | ~3K tokens | ~$0.05 |
| 实现一个中等功能 | ~10K tokens | ~$0.15 |
| 竞品分析报告 | ~8K tokens | ~$0.12 |
| 代码 Review | ~5K tokens | ~$0.08 |

月度参考预算（小型一人公司）：**$50-$200/月**

## 9. 监控与干预节奏

### 9.1 推荐的 Board 日程

**每日（10-15 分钟）：**

```
09:00 查看 Dashboard
  ✓ 有无 error 状态的 Agent？
  ✓ 有无 blocked 任务需要我解除？
  ✓ 审批队列里有没有待处理项？

09:10 快速处理
  → 批准/拒绝待审批项
  → 对 in_review 任务做决策
  → 调整优先级（如有必要）
```

**每周一（30 分钟）：**

```
1. 回顾上周完成的任务（15分钟）
   - 产出质量是否达标？
   - 哪些 Agent 表现好/差？
   - Cost vs Value 如何？

2. 设置本周优先级（10分钟）
   - 更新高优先级任务
   - 调整目标状态

3. Prompt 优化（5分钟）
   - 根据上周观察，调整 1-2 个 Agent 的 Prompt
```

### 9.2 关键监控信号

**绿灯信号（一切正常）：**
- 所有 Agent 都在 `idle` 或 `running`
- 任务按时进入 `in_review`
- 每日成本在预算内

**黄灯信号（需要关注）：**
- Agent 长时间（>2小时）在 `running` 没有进展
- 任务评论里出现"不确定"、"无法访问"、"需要更多信息"
- 某 Agent 当日消耗 > 平时 2 倍

**红灯信号（立即干预）：**
- Agent 状态变为 `error`
- 任务状态卡在 `blocked` 超过 24 小时
- 出现意外的大额 Token 消耗
- Agent 在做任务范围外的事情

### 9.3 干预工具

```sh
# 查看 Agent 最近运行记录
GET /api/agents/:agentId/heartbeat/runs

# 暂停异常 Agent
POST /api/agents/:agentId/pause

# 释放卡死的任务锁
POST /api/issues/:issueId/admin/force-release

# 手动触发心跳（测试时使用）
POST /api/agents/:agentId/heartbeat/invoke
```

## 10. 常见陷阱与规避方法

### 陷阱 1：Agent 范围蔓延

**症状**：工程 Agent 开始做营销，内容 Agent 开始写代码。

**原因**：Prompt 不够明确，或任务描述歧义。

**规避**：
- 在每个 Agent 的 Prompt 中加"禁止做什么"
- 使用 `permissions` 字段限制 Agent 可以调用的 API

```json
{
  "permissions": {
    "can_create_issues": true,
    "can_assign_issues": false,
    "can_modify_company_settings": false
  }
}
```

---

### 陷阱 2：幻觉输出（Agent 编造数据）

**症状**：分析报告里有看起来合理但实际不存在的数据。

**原因**：Agent 没有被要求标注信息来源。

**规避**：
```
在所有研究类 Agent 的 Prompt 中加入：
"数据来源必须标注。如果无法找到可靠来源，明确说明'数据不可用'，
不要基于猜测生成数字。"
```

---

### 陷阱 3：Agent 循环失败

**症状**：心跳触发 → 失败 → 重试 → 再次失败，成本快速消耗。

**原因**：没有设置失败上限和后退策略。

**规避**：
- 设置心跳重试次数限制
- 在 Prompt 中明确：连续失败 2 次后，创建一个 `blocked` 任务并停止

```
失败处理规则：
如果某个子任务连续失败 2 次：
1. 将该任务状态改为 blocked
2. 在评论中写明失败原因
3. 停止尝试，等待 Board 介入
```

---

### 陷阱 4：无效的任务分解

**症状**：CEO Agent 把大任务分解成几十个微任务，管理开销大于执行开销。

**规避**：
```
任务分解规则：
- 子任务数量不超过 7 个
- 每个子任务应该有明确的独立价值
- 如果一个子任务不到 30 分钟，考虑合并
```

---

### 陷阱 5：忽视 Activity Log

**症状**：不知道 Agent 在做什么，出了问题无法追溯。

**规避**：
- 每周审查一次 Activity Log
- 对异常行为（如大量任务状态变更）立即调查
- 设置 Agent 必须在评论中记录关键决策

---

### 陷阱 6：预算设置过高导致失控

**症状**：月底发现某个 Agent 花了 10 倍预期成本。

**规避**：
- 初期设置保守预算（可以随时调高）
- 开启 80% 预警阈值
- 公司总预算 = 各 Agent 预算之和 × 1.1（缓冲）

## 11. 一人公司的演进路径

### 阶段 1：探索期（第 1-2 个月）

**目标**：找到可工作的 Agent 配置，验证基本工作流

```
规模：1-2 个 Agent
预算：$30-50/月
时间投入：每天 30 分钟监控 + 调整
重点：Prompt 迭代，找到 Agent 的正确工作模式
```

**关键里程碑**：
- [ ] 第一个 Agent 完成了一个真实有价值的任务
- [ ] 建立了稳定的日常监控习惯
- [ ] 完成了 5 轮 Prompt 迭代优化

### 阶段 2：验证期（第 3-4 个月）

**目标**：建立可重复的工作流，产出质量稳定

```
规模：3-5 个 Agent
预算：$80-150/月
时间投入：每天 15 分钟 + 每周 30 分钟深度审查
重点：标准化任务模板，降低管理开销
```

**关键里程碑**：
- [ ] 某个核心工作流可以在没有你干预的情况下运行 3 天
- [ ] Agent 产出质量稳定，返修率 < 30%
- [ ] 建立了任务模板库（常用任务类型的标准描述）

### 阶段 3：扩展期（第 5-6 个月）

**目标**：扩大规模，追求收入增长

```
规模：6-8 个 Agent
预算：$150-300/月
时间投入：每天 10 分钟 + 每周决策会议
重点：增加 Agent 数量，覆盖更多业务领域
```

**关键里程碑**：
- [ ] 达到初始收入目标的 50%
- [ ] Agent 团队可以处理 80% 的日常任务
- [ ] 建立了完整的审批流（关键决策必须经过你）

### 阶段 4：成熟期

**目标**：业务稳定，你专注于高杠杆决策

```
你的时间分配：
20% 战略（目标设定、市场方向）
30% 质量把关（审查关键产出）
20% 系统优化（改进 Agent 和工作流）
30% 客户/增长（你独有的人际价值）
```
