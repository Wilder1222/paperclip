# Spec: Paperclip Phase 1 — Artifacts & Work Products MVP

**Branch:** master  
**Session:** 001  
**Date:** 2026-05-07  
**Status:** PENDING_APPROVAL  

---

## 1. Problem Statement

Paperclip V1 控制平面核心已经完备：Issues、Heartbeats、Budgets、Approvals、Environments（Beta）均已落地。但存在一个关键缺口：

**Agent 完成了工作，但"工作产出"不是一等公民。**

目前 Agent 的输出（生成的文件、文档、链接、截图、PR 链接）只能散落在 Issue 评论文本中，没有结构化的存储、展示和引用路径。这违反了 `doc/PRODUCT.md` 中明确的"Output-first"原则：

> "Work is not done until the user can see the result: file, document, preview link, screenshot, plan, or PR."

---

## 2. Goals (Phase 1)

### 主目标：Artifacts & Work Products MVP

让工作产出（Work Products）成为 Issue 的一等公民，让 Board 和 Agent 都能明确看到"这个 Issue 产出了什么"。

### 次目标：深度规划基础（Deep Planning 第一步）

支持 Issue 文档的"计划"类型，允许 Agent 在执行前提交规划方案供 Board 审批，避免方向偏差。

---

## 3. Scope（V1 Phase 1）

### 3.1 In Scope

#### A. `work_products` 数据表与 API
- 新增 `work_products` 表，附着在 `issues` 上
- 支持三种类型：`file`（文件附件）、`link`（外部链接/PR/文档 URL）、`document`（内联文档）
- Agent API：`POST /api/issues/:id/work-products` — Agent 提交工作产出
- Agent API：`GET /api/issues/:id/work-products` — 读取 Issue 的产出列表
- Board API：同上，复用路由

#### B. Board UI：Issue 详情侧边栏 Work Products 区域
- Issue 详情侧边栏增加 "Work Products" section
- 展示每个产出：类型图标 + 标题 + 链接/预览
- 支持 Board 手动添加和删除产出
- 产出变更记录进 activity log

#### C. Agent SDK：工作产出提交
- 在 `packages/shared` 中定义 `WorkProduct` 类型和 API 路径常量
- 在 Paperclip skill（`packages/adapters`）中提供 `submit_work_product` 工具供 Agent 调用
- Agent 执行完成时可以提交一个或多个产出

#### D. 深度规划：Issue Document "plan" 类型
- Issue 文档支持 `type: "plan"` 标记
- Plan 类型文档可以触发 Board Approval（可选，由 Issue 执行策略控制）
- 复用现有 document revision 系统，不引入新表

### 3.2 Out of Scope（Phase 1）

- 文件预览渲染（图片外的文件类型）
- S3/云存储接入（继续用现有 `local_disk` 存储）
- 工作产出的版本历史
- 跨 Issue 的产出聚合视图
- 产出的自动验证（Enforced Outcomes）

## 4. Data Model

### `work_products` 表

```sql
id             uuid        PK
issue_id       uuid        FK issues.id NOT NULL
company_id     uuid        FK companies.id NOT NULL  -- 用于公司边界验证
type           enum        'file' | 'link' | 'document'
title          text        NOT NULL
url            text        NULL  -- 对于 link 类型
storage_key    text        NULL  -- 对于 file 类型（复用现有 storage 系统）
content        text        NULL  -- 对于 document 类型（inline markdown）
created_by_agent_id  uuid  NULL  FK agents.id
created_by_user_id   uuid  NULL  FK users.id
metadata       jsonb       NOT NULL default '{}'
created_at     timestamptz NOT NULL
updated_at     timestamptz NOT NULL
```

**约束：**
- `type='link'` 时 `url` NOT NULL
- `type='file'` 时 `storage_key` NOT NULL  
- `type='document'` 时 `content` NOT NULL
- `created_by_agent_id` 和 `created_by_user_id` 至少一个非 NULL

## 5. API Contract

### Agent / Board 共用

```
POST   /api/companies/:companyId/issues/:issueId/work-products
GET    /api/companies/:companyId/issues/:issueId/work-products
DELETE /api/companies/:companyId/issues/:issueId/work-products/:id
```

**POST body:**
```json
{
  "type": "link",
  "title": "PR #123: Add user authentication",
  "url": "https://github.com/org/repo/pull/123"
}
```

**GET response:**
```json
{
  "workProducts": [
    {
      "id": "uuid",
      "type": "link",
      "title": "PR #123: Add user authentication",
      "url": "https://github.com/org/repo/pull/123",
      "createdByAgentId": "uuid",
      "createdAt": "2026-05-07T..."
    }
  ]
}
```

## 6. UI Design

### Issue 详情侧边栏 "Work Products" 区域

```
┌─ Work Products ─────────────────────┐
│  🔗  PR #123: Add user auth          │
│      github.com/org/repo/pull/123    │
│                                      │
│  📄  Implementation Plan              │
│      Created by CEO · 2 min ago      │
│                                      │
│  [+ Add work product]                │
└─────────────────────────────────────┘
```

- `link` 类型：🔗 图标 + 可点击外链
- `document` 类型：📄 图标 + 展开内联 markdown
- `file` 类型：📎 图标 + 下载链接
- Agent 提交的产出标注 "Created by {AgentName}"

## 8. Acceptance Criteria

1. Agent 可以通过 API `POST /work-products` 提交 link 类型产出并成功存储
2. Board UI Issue 详情侧边栏显示该产出（link 可点击）
3. 产出创建记录在 `activity_log`
4. Board 手动添加 link 类型产出正常工作
5. Board 可以删除产出（记录 activity）
6. Agent API 密钥正确的权限校验（只能操作自己公司的 Issues）
7. Drizzle migration 可正常运行（additive）
8. `pnpm -r typecheck` 通过
9. `pnpm test:run` 通过（新增路由的单元测试）

---

## 9. Risks

| 风险 | 缓解 |
|---|---|
| storage_key 引用现有存储系统，file 类型可能有兼容性 | Phase 1 不实现 file 上传，仅支持 link 和 document；file 类型预留字段 |
| URL 安全（开放重定向/SSRF） | 只存储 URL 字符串，Board UI 用 `rel="noopener noreferrer"` 渲染，不做服务器端代理 |
| 与现有 Issue attachment 系统重叠 | `attachments` 是任意文件上传，`work_products` 是结构化产出声明；语义不同，不合并 |

5. **Agent skill** — `paperclip` skill 新增 `submit_work_product` 工具描述
